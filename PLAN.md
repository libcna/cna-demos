# Implementation plan

This plan was written after inspecting CNA 0.1.0 (`libcna/cna` at
`10a4ef1cb4cd832f761536d77588000104947f8d`) and is kept in step with reality. The phase list with
concrete areas is [docs/ROADMAP.md](docs/ROADMAP.md); the current state is [HANDOFF.md](HANDOFF.md).

## 1. What the inspection established

* **CNA** is a C++23 reimplementation of XNA 4.0 (`Microsoft::Xna::Framework`, properties as
  `getXProperty()/setXProperty()`, events as `System::EventHandler<T>`), on SDL3 and a pluggable
  renderer layer. Module-oriented monorepo: `modules/<name>/{include,src,tests,examples}`.
* **Modules:** core, math, runtime (Game), graphics, input, audio, media (+ video-ffmpeg), content,
  content-pipeline, storage, devices, devices-ext, phone, design, diagnostics, inspector,
  graphics-ext (CNAEXT), net, gamer-services (incl. avatars), platform, c-api, 12 renderer
  families.
* **Renderers:** 14 public identities -- SDL_RENDERER, OPENGLES3, OPENGL33, WEBGL2, VULKAN, WEBGPU,
  HEADLESS, SOFTWARE, STUB, DIRECTX9, DIRECTX11, SDL_GPU, METAL, FNA3D. Compile-time selection plus
  an opt-in multi-renderer mode with runtime selection (`CNA::GraphicsRendererSelection`, latched
  at the first GraphicsDevice; `CNA_GRAPHICS_RENDERER` environment variable).
* **Build/consumption:** no installed CMake package; consumers `add_subdirectory()` a CNA source
  checkout and link the `CNA` umbrella (cna-template, cna-examples, cna-samples all do this).
  Siblings: `../sharp-runtime` (always), `../easy-gl` + `../meta-gl` (GL renderers). Submodules:
  SDL, SDL_image, SDL_mixer, draco. CNA links as `libcna.so` on Linux by default.
* **Content:** `ContentManager::Load<T>` returns by value; lookup `.xnb` → `.cnb` → literal → `.cnj`
  → loose formats (PNG/JPG/BMP/GIF/TGA/TIFF/QOI textures, WAV sounds, glTF/GLB models, MP3/OGG/
  WAV/FLAC songs, DDS cubes). SpriteFont and Effect have no loose source format at run time
  (XNB, CNB, or CNJ only); a build-time pipeline (`cna_add_content`, FreeType) makes CNB.
* **Bindings:** an experimental C API (`CNA_BUILD_C_API`, `CNA/C/cna.h`, one game per process).
  C#/.NET lives in the separate `cna-dotnet` repository.
* **Existing samples:** cna-samples (114 XNA sample ports), cna-examples (one catalog app, 248
  screens), CNA's own module examples. None is a per-concept, ID-addressed, automatable
  collection -- the gap cna-demos fills.
* **Licence:** Ms-PL (CNA), adopted unchanged by cna-demos.
* **Test environment available here:** Linux only; no GPU; Xvfb + Mesa (llvmpipe GL/GLES,
  lavapipe Vulkan); SDL dummy audio driver.

## 2. Decisions

| Decision | Choice | Why |
|---|---|---|
| Repository | dedicated `cna-demos` repo, CNA as sibling checkout | matches CNA's ecosystem; extractable by design |
| CNA consumption | `add_subdirectory(${CNA_ROOT_DIR} EXCLUDE_FROM_ALL SYSTEM)`, link `CNA` | the only supported mechanism |
| Executables | one `cna-demos`; standalone executables only for process-level features | scale, discoverability |
| Registration | self-registering static objects in OBJECT libraries | adding a demo = adding a file; no generated code |
| Source discovery | `GLOB_RECURSE CONFIGURE_DEPENDS` per category | deterministic, zero maintenance, no Python |
| Metadata | C++ designated initializers next to the code | one source of truth, checked by the compiler |
| Demo kinds | Console (function), Game (`DemoGame : Game`), Standalone | covers every CNA area without hiding the API |
| Graphics profile | HiDef project-wide, Reach demos opt in | full API available, screenshot readback |
| Renderer in tests | SOFTWARE (windowless, real rasteriser) by default | CI without a GPU or display |
| Audio in tests | `SDL_AUDIO_DRIVER=dummy` | exercises the API without hardware |
| Skips | only for declared, missing requirements | results stay honest |
| Coverage | catalog `.apis` matched against CNA's XNA member inventory, plus a generated backlog | measurable, explainable, not symbol-count inflation |
| Assets | original, generated by `tools/generate_assets.py` | clean licensing |
| Fonts | an original pixel font (`tools/pixel_font.py`) generated as an XNA font-texture sheet into `content/`, compiled at build time by CNA's `cna-content` (`CNA.FontTextureProcessor`, `cna_add_content`) and loaded with `Content.Load<SpriteFont>` | XNA's own workflow, no third-party font, no FreeType needed |
| CMake < 3.29 | static CNA (`CNA_SHARED_LIBRARY=OFF`) | CNA-DEMOS-ISSUE-001 |

Open decisions (to settle when the phase needs them):

* ~~SpriteFont asset~~ -- decided (table above): generated font-texture sheet compiled by
  `cna-content`. A TrueType `.spritefont` route stays possible later (needs FreeType and a font
  with a redistributable licence).
* **glTF/XNB test assets from CNA.** CNA's corpus files are Ms-PL; copying a few small ones with a
  notice is allowed. Decide per asset in Phases 7-8; prefer generated assets where practical.
* **C API demos** need `CNA_BUILD_C_API=ON`; add a preset and a `c_api` standalone family in Phase 14.

## 3. How work proceeds

1. Pick the next area from ROADMAP.md (phase order, unless blocked).
2. Read the CNA headers for that area; list the demos (one concept each), check against
   `cna-demos --search` and COVERAGE.md for duplicates.
3. Write the demos (DEMO_AUTHORING.md), with checks wherever the behaviour is verifiable.
4. Build; `cna-demos --validate`; run each demo on SOFTWARE (and under Xvfb on OPENGLES3 for
   graphics); look at screenshots of graphical demos.
5. `ctest`; regenerate COVERAGE.md; record any CNA problem in CNA_ISSUES.md.
6. Update ROADMAP.md status, HANDOFF.md, CHANGELOG.md; commit and push.

A batch is one coherent API area. Quality audit after each batch: re-read the batch's demos for
copy-paste drift, wrong metadata, hidden API calls, missing checks.
